# Pi Orchestrator v0.3 Design

- **Status:** Accepted
- **Scope:** Control surface, terminology, permissions, model routing, shared Workspace, Git isolation, and verification flow
- **Replaces:** The v0.2 phase-command and source-transfer architecture through the linked implementation phases
- **Implementation:** [v0.3 Implementation Plan](v0.3-implementation-plan.md)

## 1. Summary

Version 0.3 makes Pi the normal place where a human operates a Run.

The `orchestrator` host program remains necessary, but its normal job becomes bootstrap and supervision rather than a sequence of phase commands. Running `orchestrator` starts or resumes a trusted host Supervisor, constructs the cmux workspace, launches the Lead Agent inside OpenShell, and focuses the Lead pane. After that, the human works through Pi's `/orchestrator` interface and the visible Agent panes.

All Agents in a Run see the same host-owned Git worktree through direct OpenShell mounts. Source is not archived, copied into each Sandbox, or returned as a patch. The worktree root is read-only by default. At most one Agent receives a Write Lease, and only the Task's approved write roots are reopened read-write in that Agent's Sandbox. The linked-worktree `.git` file is replaced inside every model Sandbox by an opaque read-only mount, so Agents cannot discover or mutate host Git metadata.

The host Supervisor remains the only authority for state, OpenShell, cmux, Git, Checks, Reviews, and human approvals.

## 2. Why redesign v0.2

Version 0.2 established useful trust and durability boundaries, but its operating model is too host-command oriented and its source transport is heavier than this local, single-host product needs.

The redesign addresses four problems:

1. Normal work currently requires a sequence of `orchestrator` phase commands instead of being directed from the Lead Pi Session.
2. Source snapshots, temporary image contexts, archive transfer, extraction, patch export, patch replay, and patch import duplicate a source tree that can instead be shared safely.
3. Terms such as Seat, epoch, and Lens are precise but unfamiliar in agent-team tools.
4. The current design treats filesystem isolation as all-or-nothing when a read-only root plus narrow writable mounts can express Task authority directly.

The redesign retains the strongest v0.2 properties: host authority, fresh Reviews, deterministic Checks, exact digests, bounded retries, durable Reports, human commits, and transcript-independent recovery.

## 3. Goals

Version 0.3 should:

- make the Lead Pi Session the primary user interface;
- create or resume the full cmux cockpit with one bootstrap action;
- let all Agents observe one shared Run Workspace immediately;
- avoid per-Agent source copies and source archive transport;
- keep the primary Project checkout untouched;
- hide host Git metadata from every model-driven process;
- grant write access only to an approved Task and one Agent at a time;
- attribute every Workspace mutation to a Write Lease and Session;
- freeze an exact Candidate for Checks, Reviews, and human commit;
- preserve durable state without relying on any Pi transcript;
- remain local and understandable before adding distributed execution.

## 4. Non-goals

Version 0.3 will not add:

- simultaneous implementation writers;
- automatic merging among Agent branches;
- a distributed queue or remote execution host;
- a database-backed state store;
- autonomous Plan approval, commit, push, merge, deploy, or release;
- filesystem permissions as the primary security boundary;
- complete source isolation between Agents in the same Run;
- a general workflow language;
- a Stepout proving Run before this redesign is accepted and implemented.

## 5. Invariants

### 5.1 Authority

Only the trusted host Supervisor may mutate authoritative Run state, create Sandboxes, grant or revoke a Write Lease, operate host Git, satisfy Gates, or record human approval.

A Pi command or model tool may request an action. It cannot authorize or perform the corresponding state transition.

### 5.2 Context

No Session transcript is a required dependency of another Session.

Continuity must be represented by Plans, Tasks, Decisions, Briefs, Reports, Messages, Change Sets, Checks, Reviews, and Handoffs.

### 5.3 Git

No model-driven process may read or write the real `.git` entry, common Git directory, host Git configuration, index, refs, or credentials.

Only the Supervisor may stage or commit changes.

### 5.4 Workspace mutation

At most one active Sandbox in a Run may possess a read-write source mount.

That Sandbox may write only beneath the Task's approved literal write roots. Every other Agent receives the Run Workspace read-only.

### 5.5 Evidence

Checks, Reviews, and human approval must bind to the exact Candidate digest. Any Workspace change makes that evidence stale.

### 5.6 Security

No model-driven Pi process runs with host-user authority. A model may write approved paths in a disposable Run worktree, but it cannot access the primary checkout, host Git metadata, Orchestrator state, unrelated repositories, ambient credentials, or unapproved network endpoints.

## 7. Object model

```text
Project has Plans.
Run executes one approved Plan in one Workspace.
Run presents a Team of Agents.
Agent has a Role, Mailbox, and current Session.
Agent selects one allowed Model Profile.
Session runs inside one Sandbox.
Task is assigned to an Agent.
Brief initializes a Session.
Report records durable Session output.
Write Lease grants temporary Workspace mutation.
Change Set records one Write Lease's delta.
Candidate freezes the aggregate Task diff.
Checks, Reviews, and human approval accept the Candidate.
```

Agent identity is stable across Session replacement:

```text
Role
  reusable job definition

Agent
  stable Run address and Mailbox

Session
  disposable Pi context, identified by generation

Sandbox
  replaceable OpenShell execution boundary
```

The initial generic Roles should be:

```text
lead
researcher
planner
implementer
reviewer
```

Architecture and quantitative expertise should normally be Skills, project-defined Roles, or Review Focuses rather than mandatory core Role names.

## 8. Permissions

### 8.1 Effective permissions

A Role declares requested capabilities; it does not create authority by itself. Effective Session permissions are the intersection of:

```text
hard host ceiling
  intersection machine-local policy
  intersection Role capabilities
  intersection Task or Review assignment
  intersection current Run state and active Write Lease
```

Every layer may narrow the result. No Project Role, Plan, Task, model response, or Pi command may expand the host or machine-local ceiling.

### 8.2 Role schema

Version 0.3 should replace the overlapping v0.2 `access` and `sandbox` fields with explicit permission metadata:

```yaml
---
name: implementer
description: Implement one approved Task.
skills:
  - development
lifetime: task
needs:
  - task
  - plan
  - decisions
  - dependencies
  - scope
  - checks

permissions:
  source: read
  write_lease: task
  pi_tools:
    - read
    - grep
    - find
    - ls
    - bash
    - write
    - edit
  actions:
    - message
    - consult
    - report
    - handoff
    - block
    - finish
---
```

`source: read` grants visibility only after restricted-path masks are applied. `write_lease: task` makes an Agent eligible for a Task-bound Write Lease; it does not make the Workspace writable without an approved Task, literal write roots, current Session identity, and host grant.

`pi_tools` controls the tools exposed by the Pi client. `actions` controls the typed requests accepted by the client and Supervisor. Unknown permissions are invalid, and omitted permissions are denied.

The Role body remains behavioral instruction rather than security policy. `needs` controls Brief content, not authority. Model and inference settings control routing, not filesystem or workflow permissions.

### 8.3 Initial Role permissions

| Role        | Source                           | Write Lease | Principal allowed actions                                                        |
| ----------- | -------------------------------- | ----------- | -------------------------------------------------------------------------------- |
| Lead        | Read-only                        | Never       | Ask, message, consult, report, propose Plans and Decisions, request coordination |
| Researcher  | Read-only                        | Never       | Search, investigate, message, report, handoff, block                             |
| Planner     | Read-only                        | Never       | Ask, consult, report, propose a Plan, handoff, block                             |
| Implementer | Read-only plus leased Task paths | Task-bound  | Edit, message, consult, report, handoff, block, finish                           |
| Reviewer    | Frozen Candidate, read-only      | Never       | Analyze, submit one Review, handoff, block                                       |

A Reviewer may not message or consult another Reviewer before its Review is frozen. Architecture and quantitative specialists are read-only unless a separately approved Project Role explicitly qualifies for a Task Write Lease.

A Check is not an Agent Role. It receives registered argv, a read-only Candidate, private scratch, no Pi runtime, and no inference access.

### 8.4 Non-delegable authority

No Role may receive authority to:

- approve a Plan or material revision;
- expand Task scope, write roots, protected paths, or restricted paths;
- grant credentials, general network, or host-service access;
- create or delete OpenShell Sandboxes or cmux panes directly;
- read or mutate authoritative host state;
- operate host Git, create a commit, push, merge, deploy, or release;
- waive a Gate;
- mark a Check, Review, Candidate, Task, or Run accepted;
- select a Model Profile outside its approved routing policy;
- satisfy a human confirmation.

These actions either remain host-only or require a trusted human surface.

### 8.5 Enforcement

The Supervisor compiles the static permission ceiling into immutable Session configuration bound to the Role, Plan, assignment, Session generation, policy, image, and mount-table digests. Current Run state is evaluated dynamically for every request rather than embedded in that immutable digest.

Enforcement is layered:

1. the Pi client exposes only the permitted tools and typed actions;
2. the Supervisor rejects any request outside the Role, assignment, or current Run state;
3. OpenShell enforces filesystem, process, credential, and network limits even if a shell command bypasses Pi's tool conventions;
4. Write Lease and Candidate rules prevent a permitted writer from mutating at the wrong time;
5. durable Reports, Change Sets, and events record what the Session requested and changed.

Role and permission files are protected Project configuration. Any permission change invalidates affected Briefs. A capability expansion additionally requires explicit human security approval before a new Session may use it.

## 9. Model routing

### 9.1 Logical profiles and concrete routes

Project configuration selects logical Model Profiles. Machine-local configuration resolves each profile to one exact OpenShell gateway route and concrete model. Project files never contain provider credentials or machine-specific gateway addresses.

Committed routing policy belongs in `.agents/orchestrator.yaml`:

```yaml
routing:
  roles:
    lead:
      default: frontier-lead
      allowed:
        - frontier-lead
        - local-reasoning
      remote: allowed

    implementer:
      default: local-code
      allowed:
        - local-code
      remote: denied

    reviewer:
      default: independent-review
      allowed:
        - independent-review
        - quant-reasoner
      focuses:
        quant: quant-reasoner
      remote: allowed
```

Concrete routes belong in `.pi/orchestrator.local.yaml`:

```yaml
openshell:
  gateways:
    frontier: openshell-frontier
    local: openshell-local
    review: openshell-review

models:
  frontier-lead:
    gateway: frontier
    pi_model: gpt-5.6-sol
    api: openai-responses
    locality: remote
    context_window: 200000
    max_tokens: 32000

  local-code:
    gateway: local
    pi_model: qwen-local-code
    api: openai-completions
    locality: local
    context_window: 131072
    max_tokens: 16384

  independent-review:
    gateway: review
    pi_model: reviewer-model
    api: openai-responses
    locality: remote
    context_window: 200000
    max_tokens: 32000
```

Model Profile identifiers are descriptive Project-defined identifiers, not a fixed global enum. The default profiles shown above are examples rather than reserved names.

### 9.2 Agent selection

When the Supervisor creates an Agent, it selects the Role's default Model Profile unless an allowed override is supplied. The selected profile is durable Agent state.

The human may select an allowed override. A Lead may request an allowed profile for a new consultation or Agent, but a model cannot change its own profile. A request that expands inference egress, including local-to-remote routing, requires trusted human approval even when the target profile otherwise appears in Project policy.

A replacement Session and ordinary Handoff retain the Agent's selected profile. Changing it requires explicit Agent reconfiguration, a new Session generation, and a fresh Brief. Escalation should normally create a separate bounded consultation Agent instead of switching the model beneath an existing worker.

No automatic fallback may silently change locality, provider, gateway, or concrete model. An unavailable route blocks or produces an explicit escalation request.

### 9.3 Session binding

Every Session freezes:

```text
Model Profile
gateway alias and exact gateway identity
concrete model and API shape
local or remote locality
context window and output limit
reasoning configuration
pricing configuration, when present
complete route digest
```

The Agent record stores the selected logical profile; the Session record stores the exact resolved route and digest. Briefs, Reports, Reviews, Handoffs, metrics, and recovery bind to that Session route. A machine-local route change affects only a new Session and makes an unreconciled prior binding stale.

Model selection never grants filesystem, tool, workflow, credential, or human authority. Provider credentials remain at the OpenShell gateway and never enter the Sandbox.

Different Model Profiles that must run concurrently may require separate OpenShell gateways because the current integration assumes one active managed model route per gateway.

### 9.4 Review and consultation routing

Review Focuses may select an allowed Reviewer profile, as Quant does in the example. Routing policy may additionally require a Reviewer profile to differ from the Implementer's profile. Fresh Session and transcript-isolation requirements apply regardless of whether the concrete models differ.

Consultations may select an allowed profile appropriate to the question. Remote escalation remains a new bounded Agent and does not mutate an existing Agent's route.

## 10. Architecture

```text
                              TRUSTED HOST

  orchestrator bootstrap
            |
            v
  +-----------------------+       +---------------------------+
  | Host Supervisor       |<----->| cmux workspace            |
  |                       |       |                           |
  | state and Mailboxes   |       | +-----------+ +---------+ |
  | OpenShell lifecycle   |       | | Lead Pi   | | Agent A | |
  | Agent roster          |       | |           | +---------+ |
  | Write Leases          |       | | console   | +---------+ |
  | Workspace digests     |       | |           | | Agent B | |
  | Checks and Reviews    |       | |           | +---------+ |
  | human approval        |       | +-----------+             |
  | host Git              |       +---------------------------+
  +-----------+-----------+
              |
              | direct, policy-checked mounts
              v
  +-----------------------------------------------------------+
  | Dedicated Run Workspace                                  |
  | host Git worktree; never the primary Project checkout     |
  +-----------------------------------------------------------+
              ^                 ^                  ^
              | read-only       | narrow read-write| read-only
       +------+-------+  +------+-------+   +------+-------+
       | Lead Sandbox |  | Writer       |   | Review       |
       | Pi + client  |  | Sandbox      |   | Sandbox      |
       +--------------+  +--------------+   +--------------+
```

The Supervisor is trusted software, not an Agent Role. It should normally run quietly in the background and expose a host-local control API. Every Pi process, including the Lead, remains inside OpenShell.

The Pi client extension translates `/orchestrator` commands and model-facing tools into typed requests. The Supervisor validates those requests against current state before acting.

The host program cannot be eliminated without moving host authority into Pi or recreating the same service under another name. A Sandbox-local extension cannot safely create its own Sandbox, operate cmux, read authoritative state, or commit through host Git. The minimal split is therefore a trusted Supervisor outside OpenShell and an untrusted Pi client inside it.

## 11. Normal user experience

### 11.1 Bootstrap

The default command, run from a cmux-created terminal, should be:

```sh
orchestrator
```

An explicit equivalent may remain available:

```sh
orchestrator open
```

Bootstrap performs the following:

1. discover and validate the Project;
2. acquire single-writer Supervisor ownership;
3. start or connect to the Project Supervisor;
4. create or reconcile the cmux workspace;
5. create or resume the Lead Agent and its OpenShell Sandbox;
6. open or focus the Lead Pi pane;
7. project current status through the Pi extension.

cmux 0.64.22 grants workspace and pane control through an authenticated socket inherited by terminals that cmux creates. The Supervisor must preserve that boundary. If `orchestrator` is invoked from an ordinary terminal, it may open the Project with cmux's public launcher and explain the remaining bootstrap step, but it must not read, persist, or weaken cmux's socket credential. A truly single-action external launcher requires a future authenticated cmux launch API.

The user should not need to invoke `validate`, `approve`, `start`, `implement`, `check`, `review`, and `commit` as a normal sequence of shell commands.

### 11.2 Pi control surface

One `/orchestrator` namespace should expose the normal workflow:

```text
/orchestrator status
/orchestrator plan
/orchestrator agents
/orchestrator tasks
/orchestrator message
/orchestrator handoff
/orchestrator review
/orchestrator approve
/orchestrator commit
```

The extension may render status and forms, but it does not become authoritative. Model-facing tools remain small and typed:

```text
status
report
message
ask
consult
handoff
block
propose_decision
finish
```

Host CLI operations such as `doctor`, `canary`, `reconcile`, `status`, and `stop` remain available for installation, diagnostics, automation, and recovery. Phase-oriented commands may remain as an advanced or test API, but the README should not present them as the primary workflow.

### 11.3 cmux layout

The default layout should use:

- a persistent Lead Pi pane on the left;
- a right column of stacked active Agent panes;
- short titles containing Agent, Role or Review Focus, Model Profile, and Task;
- a transient trusted host pane only when human confirmation is required.

The Lead pane is the cockpit. There is no always-visible Supervisor terminal unless diagnostics require one.

Each Agent pane contains only the trusted host-side OpenShell attach command and the Sandbox-local Pi interface; it does not place Pi on the host. Pane presence is a projection, not workflow authority. Closing a pane never completes a Task: the Supervisor reattaches it to the current Session when possible or performs a durable Session replacement.

## 12. Workspace and Git model

### 12.1 Planning Workspace

Planning must not inspect the human's primary checkout directly because ignored or untracked secrets may exist there.

The Supervisor creates a clean detached Git worktree at the exact planning commit and mounts it read-only into planning Agents. Its `.git` entry is masked. This is one Git materialization for the planning effort, not one copy per Agent.

Planning Sessions emit a validated Plan draft as a host-side Artifact. They do not modify repository files.

### 12.2 Plan publication

A Pi-first workflow needs a trusted path from a Plan draft to committed Project knowledge. The recommended flow is:

1. the Supervisor validates and freezes the generated `plan.md` and `tasks.yaml`;
2. it creates a reserved branch and worktree from the planning commit;
3. it writes only the validated Plan files into that isolated worktree;
4. a trusted cmux pane displays the exact Plan contents, repository diff, and digest;
5. one human confirmation authorizes the exact one-line Plan commit and Plan approval;
6. the approval binds to that commit and Plan digest;
7. the same worktree becomes the approved Run Workspace.

This keeps the primary checkout unchanged and avoids asking the user to leave cmux to copy model output. An already committed human-authored Plan can enter at step 6.

### 12.3 Run Workspace

An approved Run owns one branch and one linked Git worktree outside the primary checkout:

```text
branch     <branch-prefix><run-id>
path       <worktrees-root>/<project-id>/<run-id>
base       exact approved commit
```

Git creates this Workspace once. Every Run Agent receives a direct projection of the same path, so an allowed write is visible immediately in every other Sandbox.

There is no normal source archive, upload, extraction, per-Agent project copy, patch export, patch replay, or copy-back step.

Workspace ownership does not make its source trusted. Content is untrusted while a Write Lease is active and remains an unaccepted Candidate until its Gates pass. The host may inspect, hash, and stage it through hardened adapters, but it must never execute Project hooks, scripts, builds, tests, or generated binaries outside an OpenShell Sandbox.

### 12.4 Sandbox projection

Every model Sandbox begins with the complete Run Workspace mounted read-only:

```text
host Run Workspace       -> /workspace/project       read-only
opaque host sentinel     -> /workspace/project/.git  read-only
opaque restricted masks  -> configured source paths  read-only
Session input            -> /workspace/input         read-only
Sandbox output           -> /sandbox/output          read-write
private build scratch    -> /sandbox/build           read-write
private cache            -> /sandbox/cache           read-write
temporary space          -> /tmp                     read-write
```

The `.git` mask must be an opaque regular file mounted over the linked-worktree `.git` file. It must reveal neither the real pointer contents nor the common Git directory. Removing, renaming, or replacing the mask must fail.

Project configuration may also declare existing tracked `restricted_paths` that no model should read. Files are replaced by opaque file mounts and directories by empty read-only directory mounts in every Agent, Check, and Review Sandbox. Protected paths and restricted paths are different: protection denies an accepted change, while restriction denies visibility. A write root may not contain or overlap a restricted path.

An Agent holding the Write Lease receives additional nested mounts:

```text
approved host write root -> matching Workspace path   read-write
```

The root remains read-only. Only explicit Task write roots are reopened.

### 12.5 Write roots

Task configuration should distinguish human-readable source scope from mountable write authority:

```yaml
scope:
  - src/pricing/**
  - test/pricing/**

write_paths:
  - src/pricing
  - test/pricing
```

`write_paths` must be literal repository-relative files or directories. A Task that may add a file grants its nearest approved parent directory, not the repository root.

Before Sandbox creation, the Supervisor must:

- normalize each path without shell expansion;
- reject absolute paths, `..`, NUL bytes, and platform-ambiguous forms;
- resolve every existing component beneath the canonical Run Workspace;
- reject symlinked mount roots and escapes;
- reject roots that overlap `.git` or host-owned paths;
- reject roots that overlap a restricted path;
- reject roots broad enough to include a configured protected path unless that protected descendant is independently masked read-only;
- record the exact resolved mount table in immutable Session configuration.

Post-work validation still compares every changed path with `scope` and protected patterns. Mounts limit capability; validation determines whether the resulting Candidate is acceptable.

### 12.6 Workspace manifests

Workspace authority cannot rely only on `git diff`, which omits ignored files and needs separate handling for untracked content. After every writer is gone, the host computes a bounded manifest over every Workspace entry except the real `.git` entry.

The sorted manifest records path, entry type, executable mode, byte count, content digest, and symlink target without following symlinks. It includes tracked, untracked, and ignored paths. Unsupported devices, sockets, FIFOs, changing files, unsafe links, and unexpected multiply linked entries block validation.

The host separately reads NUL-delimited Git status and diff evidence through its scrubbed adapter. The Workspace manifest detects all filesystem mutation; Git evidence defines the exact committable source change. Both feed the Change Set and Candidate digests.

### 12.7 Why permissions and Pi command rules are insufficient

Unix ownership is not the primary boundary because directory permissions, bind-mount ownership translation, container user mapping, symlinks, and process capabilities make it easy to protect the wrong object. OpenShell's filesystem projection and runtime canaries provide the enforceable boundary.

Pi tool permissions may discourage commands such as `git commit`, `git reset`, or `git worktree`, but they are defense in depth only. A shell tool can invoke another program that performs the same operation. Security comes from the absence of real Git metadata and host paths, not from recognizing command text.

## 13. Write Lease and Change Set lifecycle

### 13.1 Acquiring a Write Lease

A Write Lease binds:

```text
Run
Task
Agent
Session
Session generation
Workspace generation
baseline Workspace digest
literal write roots
scope and protected-path policy digests
OpenShell Sandbox and mount table
start time
expiry and renewal counter
```

The Supervisor grants a lease only when:

- the Plan approval and Task Brief are fresh;
- the Task is ready or in bounded rework;
- no other Write Lease exists;
- no frozen Candidate is under Check, Review, or approval;
- the Workspace matches its expected branch, commit, generation, and digest;
- the required OpenShell mount profile and canary are valid.

Because OpenShell filesystem policy cannot safely revoke a live writable path, gaining or losing write authority requires a new Sandbox. A Handoff carries durable context when a Session must be replaced.

Lease expiry begins forced revocation; it does not make the Workspace stable by itself. The Supervisor must terminate the writable Sandbox and verify that its mount is gone before clearing the lease or freezing a Candidate.

### 13.2 Releasing a Write Lease

When the Agent reports completion, blocks, fails, or is interrupted, the Supervisor:

1. freezes new model actions for that Session;
2. obtains the Agent's durable Report when possible;
3. terminates and deletes the writable Sandbox;
4. verifies that no Sandbox retains a read-write Run mount;
5. scans the Workspace and computes its new manifest and digest;
6. derives the exact path and content delta from the lease baseline;
7. validates scope, protected paths, file types, sizes, and policy;
8. records an immutable Change Set;
9. advances the Workspace generation;
10. notifies current Agents of the stable change.

A Change Set records who changed the Workspace operationally without pretending to establish source authorship:

```text
Agent and Session identity
Task and Write Lease
baseline and result Workspace generations
baseline and result digests
changed paths and content metadata
start and end times
Report reference
```

Git commits retain the human author and committer selected at approval. Agent attribution remains Orchestrator audit evidence and need not be encoded as multiple Git authors.

### 13.3 Unexpected changes

A Workspace change with no matching active Write Lease blocks the Run. A change outside the lease's write roots or Task scope blocks the Task. The Supervisor does not reset, clean, stash, discard, or silently adopt unexpected content.

Recovery may attribute a delta to an interrupted lease only when the persisted lease, actual Sandbox identity, mount table, baseline digest, and observed Workspace state all agree.

## 14. Shared visibility and Workspace generations

Direct mounts make writes visible to other Agents immediately. That is useful for collaboration but does not make an in-progress tree a stable input.

The Workspace therefore has a monotonic generation and one of these phases:

```text
stable
mutating
frozen
```

While a Write Lease is active, the Workspace is `mutating`. Read-only Agents may inspect it, but they must not treat it as a coherent Candidate or begin a Gate-producing action from it.

After lease release and successful validation, the Supervisor advances the generation and emits a structured `workspace_changed` Message containing:

```text
old and new generation
Change Set ID
result digest
changed paths
affected Tasks and Briefs
```

The Pi extension marks affected source context stale. Agents reread relevant files instead of assuming that earlier prompt content changed when the filesystem changed.

Shared filesystem visibility does not relax minimum sufficient context. A Brief still injects only the Role, Task, Decisions, Reports, Skills, and source anchors needed for the Session; the read-only Workspace is retrieval capability, not prompt content.

## 15. Candidate, Checks, Reviews, and commit

### 15.1 Candidate freeze

A Candidate is the complete uncommitted Task result at one stable Workspace generation. It binds:

```text
Plan and approval digest
Task and input commit
Workspace generation and manifest digest
ordered Change Set IDs
changed paths and content metadata
host diff digest
scope and protected-path policy digests
```

Before freezing a Candidate, the Supervisor must prove that every writable Sandbox is gone. No new Write Lease may begin until the Candidate is accepted, rejected for rework, or explicitly discarded by the human.

### 15.2 Checks

Every authoritative Check runs in a fresh OpenShell Sandbox with:

- the same frozen Run Workspace mounted read-only;
- no Pi runtime or inference route;
- no credentials or general network;
- private writable build, cache, and temporary paths;
- a registered argument array and allowlisted environment;
- Candidate digests verified before and after execution.

Project Check configuration should redirect ordinary outputs such as Cargo targets and package caches into private scratch. A Check that inherently rewrites source is unsupported in the initial v0.3 path and must fail with a clear configuration error rather than receiving general Workspace write access.

### 15.3 Reviews

Every Review uses a fresh Agent Session and fresh read-only Sandbox. It receives the frozen Candidate, current Plan and Task, passing Check evidence, applicable Decisions, and one Review Focus.

It receives no implementer transcript, hidden reasoning, prior Reviewer finding, or claim that the Candidate is correct. Review results are frozen independently before any cross-review synthesis.

### 15.4 Human commit

After every required Check and Review passes, the Supervisor opens a trusted host confirmation surface in cmux. It displays the exact Task, Plan revision, branch, Candidate and diff digests, changed paths, Check results, Review verdicts, and proposed one-line subject.

The model-facing Pi pane may request this action but cannot answer it. Confirmation must occur in the host-owned surface and produce a durable intent before Git mutation.

The existing scrubbed Git adapter should be retained. It stages only the exact approved Candidate, verifies staged modes and blobs, creates the commit without Project hooks or ambient Git configuration, and advances the Run branch with compare-and-swap semantics. The resulting clean Workspace becomes the next Task's baseline.

Any digest change between Candidate freeze and commit invalidates Checks, Reviews, and approval.

## 16. Team coordination

### 16.1 Agent roster

The Run stores an Agent roster rather than a Seat registry. Each Agent has:

```text
stable Agent ID
Role and Model Profile
current Session and generation
status
assigned Task or Review
Mailbox counts
cmux pane binding
```

The Team is the projection of this roster in Pi and cmux. It does not introduce another state owner.

### 16.2 Task list

The Supervisor owns the shared Task graph and current facts. Agents may request assignment, claim, progress, block, or finish transitions. They may not mark a Task accepted or claim that a Gate passed.

One implementation Task may hold the Write Lease. Research, planning, consultation, and read-only analysis may proceed in parallel when they do not require a frozen Candidate.

### 16.3 Messages

Agents address Agents or Roles. Only the Supervisor resolves a current Session and Sandbox.

Messages remain durable host-owned records with stable IDs, delivery acknowledgement, deduplication, and Session-generation binding. Large data remains in immutable Artifacts rather than the Message channel.

There is no shared mailbox directory in the Workspace and no direct Agent-to-Agent socket.

### 16.4 Handoffs

A Handoff replaces a Session without replacing its Agent. It contains the current Task, Workspace generation, relevant Change Sets, Reports, blockers, source anchors, and next action. It never injects the predecessor transcript.

## 17. Human authority inside a Pi-first workflow

Pi-first must not mean model-authorized.

The Supervisor must use a trusted host surface for:

- Plan approval;
- material Plan revision;
- expanded Task scope or write roots;
- protected-path or security-policy expansion;
- Gate waiver;
- commit;
- destructive discard.

The recommended initial surface is a short-lived cmux pane started directly by the Supervisor. It displays an immutable proposal digest, accepts explicit human input from the terminal, records the local approving identity, and closes after success or cancellation.

A confirmation typed into the Lead Pi conversation is ordinary untrusted Message content and cannot satisfy a human Gate.

## 18. OpenShell requirements

Direct Workspace projection requires the local OpenShell Docker driver to permit carefully constrained host bind mounts. This is a privileged operator capability and must be opt-in in machine-local gateway configuration.

A direct Docker spike has already demonstrated the required root read-only, nested read-write, live visibility, and `.git` mask behavior on the development host. The end-to-end OpenShell path is not yet proven: OpenShell 0.0.106 disables Docker bind mounts by default and rejects the operation until the operator explicitly enables them. The OpenShell canary, not the Docker spike, is the release gate.

Bind-mount capability should be enabled only on a dedicated local OpenShell gateway or driver instance whose control credential is available to the trusted Supervisor. It must not be enabled on a shared gateway that accepts Sandbox creation requests from untrusted clients. The Pi image receives neither the OpenShell CLI authority nor its control token.

The Orchestrator adapter must narrow that capability further:

- accept sources only beneath the configured planning and Run worktree roots or an Orchestrator-owned sentinel root;
- accept destinations only beneath documented Sandbox paths;
- inspect the resulting Sandbox mount table rather than trusting requested configuration;
- reject writable root mounts and unexpected nested mounts;
- reject a missing or readable `.git` mask;
- reject unsupported drivers, remote gateways, policy versions, or mount semantics;
- pin OpenShell, images, Pi, runtimes, extension, and policy digests;
- fail closed before launching Pi.

The redesigned canary must prove at minimum that:

1. the Workspace root rejects writes;
2. an approved nested write root accepts writes only for the writer;
3. sibling and protected paths remain read-only;
4. restricted paths reveal no original content;
5. another Agent's read-only projection sees an allowed write;
6. `.git` is opaque, unreadable as Git metadata, and cannot be removed;
7. the real common Git directory is absent;
8. host state, home, credentials, sibling repositories, Docker socket, and SSH agent are absent;
9. unapproved network and host-local services are denied;
10. Sandbox termination removes the writable mount before a Candidate freezes;
11. the Candidate digest does not change during read-only Checks or Reviews.

The direct-mount profile remains disabled until this canary passes on the exact installed OpenShell and compute-driver versions.

## 19. State and configuration changes

Run state should add:

```text
Workspace path, branch, phase, generation, and digest
Agent roster, selected Model Profiles, Session generations, and resolved route digests
current Write Lease, if any
immutable Change Set references
current Candidate, if any
actual mount and Sandbox provenance
trusted approval-surface intents and results
```

Task configuration should add literal `write_paths`. The existing `scope` remains the semantic and post-work validation boundary. Committed Project configuration should distinguish `protected` paths from `restricted_paths` and define per-Role Model Profile policy; machine-local configuration may add restrictions but must not remove committed ones.

Machine-local configuration should add:

```text
bind-mount capability acknowledgement
allowed worktree roots
sentinel path
driver-specific mount settings
private build and cache defaults
concrete Model Profile routes and gateway bindings
```

Runtime state remains outside the Project and invisible to Sandboxes. The filesystem store remains appropriate while there is one trusted Supervisor writer.

The implementation should use a new state schema version and fail closed on unfinished v0.2 Runs. Automatic migration is unnecessary before any real proving Run, but old state may be retained for diagnostics.

## 20. Recovery

On restart, the Supervisor reconciles:

```text
Project and Run state
Run branch and Workspace registration
Workspace manifest, phase, generation, and digest
current Write Lease
actual OpenShell Sandboxes and mount tables
Agent Sessions and Connections
cmux workspace and panes
Messages, Reports, Change Sets, Checks, Reviews, and approvals
```

A missing cmux pane never implies completion. A running read-only Sandbox may be reattached. A missing Session may be replaced from its Brief, Reports, Messages, and Handoff.

If a persisted Write Lease exists, recovery first removes or proves the absence of its writable Sandbox before reading the Workspace as stable. A write-capable Sandbox that has no exact current lease blocks the Run.

The Supervisor never resets, cleans, stashes, discards, or commits unexpected Workspace content automatically.

## 21. Migration from v0.2

The v0.3 design and replacement ADRs are accepted. Existing v0.2 runtime behavior remains implemented until each migration phase replaces it; unfinished version-one Runs are not migrated.

After acceptance:

1. record new ADRs for the Pi-first control surface, terminology, Model Profiles, direct Workspace projection, Write Lease, and Candidate lifecycle;
2. mark conflicting portions of the old ADRs superseded rather than rewriting history;
3. update `docs/contracts.md` and the state schema;
4. implement and prove the OpenShell mount canary before changing source flow;
5. adapt Run, Agent, Session, Check, Review, and commit logic;
6. add the Pi control console and one-action cmux bootstrap;
7. remove archive, extraction, patch-export, replay, and import paths only after replacement coverage passes;
8. rewrite the README around bootstrap and Pi operation;
9. run the generic example before considering Stepout.

The likely supersession set includes ADRs 0004, 0006, 0007, 0008, and 0011 through 0016. Some decisions remain valid in purpose but require new mechanics or terminology.

## 23. Resolved design choices

1. The persistent left pane and Agent are named `lead`; Orchestrator status is rendered inside Pi.
2. Every writable Task declares literal `write_paths`; validation may suggest paths but does not infer authority.
3. Source-mutating authoritative Checks are rejected initially; ordinary build output uses private scratch.
4. Human approval uses a transient trusted cmux pane.
5. Phase commands remain a documented low-level API for scripts, diagnostics, and tests but leave the primary getting-started path.
6. Read-only Agents may inspect a `mutating` Workspace but cannot emit source-bound durable conclusions until the next stable generation.
7. One immutable proposal and one human confirmation may authorize Plan publication and approval when the displayed Plan and exact commit bytes are identical.
8. **External bootstrap:** Require the first `orchestrator` command to run inside cmux, or pursue an upstream authenticated API that can launch the full layout from an ordinary terminal? Recommendation: require cmux for v0.3 and do not weaken socket authentication.
9. **Pi namespace:** Keep the v0.2 `/orchestrate` verb or use `/orchestrator` for the unified console? Recommendation: `/orchestrator`, matching the product and host command.

## 24. Design influences

The terminology and operating model intentionally align with established agent-team systems where doing so does not weaken the trust model:

- [Claude Code agent teams](https://code.claude.com/docs/en/agent-teams) uses a lead, teammates, a shared task list, and mailboxes.
- [`pi-agent-teams`](https://github.com/tmustier/pi-agent-teams) uses a leader, teammates, shared workspaces by default, and optional worktrees.
- [`pi-agentteam`](https://github.com/LinYS77/pi-agentteam) uses a leader, workers, Roles, Tasks, Reports, and a Mailbox.
- [Codex's Linux sandbox](https://github.com/openai/codex/blob/main/codex-rs/linux-sandbox/README.md) demonstrates explicit read-only Git-metadata carve-outs as a filesystem security control.
- [OpenShell Docker driver configuration](https://github.com/NVIDIA/OpenShell/blob/main/crates/openshell-driver-docker/README.md) and the [OpenShell policy schema](https://docs.nvidia.com/openshell/latest/reference/policy-schema) define the mount and isolation capabilities that the implementation must validate.

Pi Orchestrator deliberately keeps stronger authority, review freshness, human Gate, and transcript-independence rules than a lightweight agent-team extension because it controls security-sensitive software-development state.
