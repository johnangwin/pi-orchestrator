# Pi Orchestrator v0.3 Implementation Plan

- **Status:** Active; Phase 2 complete
- **Design input:** [Pi Orchestrator v0.3 Design](v0.3-design.md)
- **Execution target:** Generic example Project only
- **Stepout:** Explicitly deferred

## 1. Objective

Replace the v0.2 phase-command and source-transfer architecture with the v0.3 Pi-first, shared-Workspace design while preserving the proven authority, durability, isolation, Check, Review, commit, and recovery guarantees.

This is a hard architectural migration, not a feature layered permanently beside v0.2. The repository must remain buildable and testable at every commit, but it will not support selecting between two runtime architectures.

## 2. Planning assumptions

The plan implements the accepted choices in the v0.3 design:

1. The left pane is the `lead` Agent; the Supervisor has no permanent pane.
2. Tasks declare literal `write_paths`; the Orchestrator does not infer write authority from arbitrary globs.
3. Source-mutating authoritative Checks are unsupported initially.
4. Human actions use a transient trusted cmux pane.
5. Low-level CLI commands remain available for diagnostics, tests, and automation but are not the primary workflow.
6. Read-only Agents may inspect a mutating Workspace but may not emit source-bound durable conclusions until the next stable generation.
7. One human confirmation may approve an exact Plan publication and commit when both bind to identical bytes.
8. Full bootstrap begins inside a cmux-created terminal for v0.3.
9. The Pi namespace is `/orchestrator`.
10. Roles select Project-defined logical Model Profiles through per-Role default and allowed-profile policy; concrete routes remain machine-local.
11. A model-route or locality change creates a new Session generation or separate consultation; there is no silent local-to-remote fallback.
12. No unfinished v0.2 runtime state requires migration.

Implementation should not begin until these assumptions and the design's permission and model-routing policies are accepted. A changed assumption updates the design and this plan before code changes start.

## 3. Delivery rules

- Keep each commit limited to one named behavior or one mechanical migration.
- Run formatting, type checking, unit tests, and build after every commit.
- Keep the existing CLI as a temporary integration harness until the Supervisor and Pi console reach parity.
- Do not retain a runtime fallback to source archives or patch import after shared-volume projection passes its release gate.
- Do not delete v0.2 source-transfer code until no active path imports it.
- Do not weaken an isolation rule merely to keep a test or existing adapter convenient.
- Do not run Stepout during this plan.
- Stop at a proof gate when the installed OpenShell or cmux contract cannot enforce the design.

## 7. Phase 1: Prove shared OpenShell Workspace volumes

This phase proves the highest-risk external dependency without launching a model or changing the production Session path.

### Changes

- Pin the exact installed OpenShell CLI, gateway, driver, and image versions used by the proof.
- Add a trusted Docker volume adapter that creates, labels, inspects, and removes plain local named volumes.
- Reject bind-backed volumes, driver options, label mismatches, remote gateways, and raw mount input.
- Add a typed volume mount descriptor to `OpenShellClient` with normalized source subpaths and fixed Sandbox destinations.
- Add a disposable Workspace-volume canary that creates:
  - one complete read-only Workspace root;
  - one nested writable Task root;
  - no Git metadata in the projected `project` subtree;
  - an opaque restricted-file mask;
  - an empty restricted-directory mask;
  - a second read-only Sandbox over the same named volume.
- Inspect the actual in-Sandbox mount table and bind it to canary evidence.
- Keep shared-volume projection disabled for ordinary Sessions until later phases replace the v0.2 path.

### Required tests

1. Root writes fail.
2. The approved nested root accepts create, replace, rename, and delete operations.
3. Sibling writes fail.
4. Protected descendants remain read-only.
5. Restricted content is not observable.
6. `.git` and real Git metadata are absent and cannot be created at the read-only root.
7. Supervisor-only volume paths and the Docker backing path are inaccessible.
8. A write becomes visible through the second read-only Sandbox.
9. Host state, home, credentials, sibling repositories, Docker socket, SSH agent, and host-local services remain inaccessible.
10. Sandbox deletion removes the writable projection.
11. Unsupported driver, bind-backed volume, disabled capability, or mount mismatch fails before Pi launch.

### Proof gate

Proceed only when the live canary passes against the exact supported environment. The Docker-only spike is not sufficient.

### Live proof result

The 2026-08-19 named-volume proof passed against OpenShell 0.0.106 and Docker 29.5.2 with hard Landlock enabled. It verified native `ext4` mounts, root read-only behavior, narrow writes, protected descendants, restricted masks, cross-Sandbox visibility, Git absence, host isolation, and complete cleanup. See [OpenShell Workspace-Volume Proof](proofs/openshell-workspace-volume.md). Phase 2 may proceed.

### Commit

```text
Prove shared OpenShell workspace volumes.
```

## 8. Phase 2: Introduce Agent terminology

This is a mechanical protocol and state migration. It must not change scheduling or filesystem behavior.

### Changes

- Rename Seat to Agent in source names, schemas, records, Messages, Mailboxes, Reports, metrics, cmux bindings, and user-facing text.
- Rename Session epoch to Session generation.
- Rename `seat.ts` to `agent.ts` and update exports.
- Advance durable Run state and Link protocol versions.
- Reject v0.2 state with an explicit unsupported-state diagnostic; do not auto-migrate it.
- Update all fixtures and test names mechanically.
- Preserve stale-generation rejection and contiguous Session history semantics.

### Required tests

- Agent roster and Session-generation invariants match the old proven behavior.
- A stale generation cannot deliver a Message, emit an event, replace a Session, or bind a pane.
- Recovery does not infer Agent identity from titles or terminal state.
- Active source contains no Seat or epoch terminology except versioned compatibility diagnostics.

### Outcome

Complete. Runtime identity, protocol fields, durable records, sandbox client data, recovery, metrics, and cmux projection now use Agent and generation terminology. Run and planning state use schema version 2, Link and Pi client traffic use protocol version 2, and unfinished version-one state fails with an explicit unsupported-state diagnostic. Scheduling and filesystem behavior are unchanged.

```text
Rename Seats and epochs to Agents and generations.
```

## 9. Phase 3: Enforce Role permissions

### Changes

- Add strict permission schemas for source visibility, Write Lease eligibility, Pi tools, and Orchestrator actions.
- Replace Role `access` and `sandbox` fields.
- Add the initial Role permission matrix to generated Project templates.
- Compute an immutable permission-ceiling digest from host limits, local policy, Role, and assignment.
- Include that digest in Session configuration, Brief freshness, Plan approval evidence, and recovery checks.
- Generate the Pi tool list from permissions rather than a `read` or `write` profile string.
- Intersect the permission ceiling with current Run state when validating every model-facing action in both the Pi client and Supervisor-side handler.
- Keep a hard-coded non-delegable authority ceiling outside Project configuration.
- Make permission expansion visible in human Plan approval and invalidate affected approvals and Briefs.

### Required tests

- Unknown, contradictory, or omitted-required permissions fail validation.
- Read-only Roles cannot qualify for Write Leases or receive write tools.
- Implementer eligibility alone does not grant a writable mount.
- Reviewer coordination is denied before its Review freezes.
- A forged client action is rejected by the host even when the client-side check is bypassed.
- Project configuration cannot request Git, Sandbox, cmux, Gate, credential, or human authority.
- Permission changes invalidate Sessions and evidence bound to the prior digest.


## 10. Phase 4: Add policy-bound Model Profiles

### Changes

- Replace the fixed logical-model enum with validated, descriptive Project-defined Model Profile identifiers.
- Remove model selection from Role files and define committed per-Role routing policy with a default profile, allowed profiles, Review Focus overrides, and remote-egress policy.
- Resolve each Model Profile through machine-local configuration containing its OpenShell gateway, Pi model, locality, API, context limit, and optional reasoning and accounting metadata.
- Store the selected Model Profile as durable Agent state and the exact resolved route and route digest as immutable Session state.
- Validate an explicit Agent profile override against the Role policy before creating the Agent.
- Prevent model-facing tools and Messages from changing their own Agent's Model Profile.
- Start a new Session generation with a fresh Brief when a continuing Agent changes profile; keep escalation as a separate bounded consultation Agent by default.
- Prohibit automatic fallbacks that change provider or locality, and require trusted human approval before expanding inference egress from local to remote.
- Bind Briefs, Reports, Reviews, Handoffs, metrics, and recovery decisions to the selected profile and resolved-route digest.
- Permit concurrently active profiles through separately configured OpenShell gateways where the gateway implementation supports only one managed route.
- Keep model selection independent from Role permissions and non-delegable host authority.

### Required tests

- A frontier Lead and local Implementer resolve and run concurrently without changing each other's routes.
- Arbitrary valid Model Profile identifiers work without changing a fixed enum.
- Missing profiles, gateways, model names, or locality declarations fail closed.
- An Agent profile override outside the Role's allowed set is rejected.
- A local-only Role cannot resolve to a remote profile or fallback.
- A model-originated request cannot switch its own profile.
- Route configuration drift makes the old binding stale and requires a new Session generation.
- A normal Handoff retains the selected profile, while an approved profile change creates a new generation.
- Review Focus may select an independently allowed Quant profile.
- Selecting a stronger model does not expand source, tool, action, Git, or Sandbox permissions.

### Commit

```text
Add policy-bound Model Profiles for Agents.
```


```text
OpenShell Workspace-volume canary
```

## 25. Review checkpoints

Human review is required at these points:

1. **Contract checkpoint:** accept the v0.3 design, open-question choices, ADRs, and schema contracts.
2. **Mount checkpoint:** inspect the live OpenShell mount canary before changing Session source flow.
3. **Writer checkpoint:** inspect one real Write Lease, mount table, Change Set, and Candidate before adapting Gates.
